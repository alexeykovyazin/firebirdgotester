## Часть 2. Дополнение 1 — подробная итоговая статистика (лог + UI)

Требование: в конце прогона — подробная сводка в логе; в UI — доступна в любой
момент (в т.ч. отдельной страницей). **Не блокирующе** = только чтение
уже собранных in-memory структур под существующими RWMutex/atomic, никаких
запросов к серверу БД; вызов безопасен и посреди прогона, и во время остановки.

### 2.1. Что уже есть (не дублируем)

- `reporter.ReportFinal()`: сводная строка, распределение операций/ошибок(видов),
  латентность-бакеты, системная конфигурация (metrics/reporter.go:171).
- `printExtendedSummary` (main.go:244): extended-счётчики, таблицы
  вариантов/[completions].
- `[emul] final` (main.go:305): score, ok/total, строка инвариантов, пики памяти.
- Данные, которые уже собраны, но НЕ попадают в итог: per-unit
  `OutcomeStats` (worker/worker.go:1336 `GetUnitStats`: OK/Conflict/Rejected/
  Failure/AvgMs/MaxMs), таксономия ошибок `ops.ErrorStats`
  (Total/Expected/Unexpected/Retryable + counts), series (EmulState, кэп 120
  точек), stop-логи ramp (только текстом).

### 2.2. Чего не хватает (добавляем счётчики)

Все — атомики/под мьютексами, заполняются по ходу прогона:

1. **Пер-юнит таблица** — уже считается, только вывести: топ по Failure,
   колонки unit/attempts/ok/conflict/rejected/failure/avg/max.
2. **Ошибки полным текстом**: map «нормализованный текст → count» +
   first/last seen (кэп 50 записей). Сейчас в Report.ErrorCounts только виды
   («unknown_error», «deadlock») — по ним не понять, что именно произошло.
3. **Инварианты структурно** (сейчас строка в EmulState + лог-строки):
   checks, ok, transientRetries, hardStrikes, disabled(0/1)+reason,
   max длительность проверки.
4. **Остановка**: stopTimedOut, reaped (ramp), длительность фазы остановки.
5. **Пул соединений**: min/max открытых конн за прогон, счётчик rebuildConn
   (успешных/неудачных) — worker.
6. **Limbo подробно**: generated (попытки limbo-завершений), resolved,
   unresolved на конец, разбивка способов (commit/rollback/2pc), пик
   unresolved, максимальный возраст разрешённой транзакции. Расширить
   ExtendedCounters + sidecar StartLimboRecovery.
7. **Поминутный таймлайн**: ok/err юнитов и средняя латентность за минуту;
   хранить весь прогон (кэп 1440 точек = 24 ч; для дефолтных 60 мин — 60
   точек). Источник — тот же тикер, что series, но без кэпа 120.
8. **Фактические длительности фаз** (warmup/main/cooldown по временам
   переходов планировщика, а не конфиг).
9. **Эхо конфигурации** в итоге: DSN (замаскированный), профиль, conn min/max,
   tx-timeout, флаги extended/no-limbo/cancel-hard-drop/grace, версия сборки.

### 2.3. Вывод

- **Лог**: новый блок `=== FINAL DETAILED SUMMARY ===` печатается один раз при
  остановке (после ReportFinal): пункты 2.2.1–9 + существующие таблицы.
- **Файл**: тот же текст в `<csv>_final_summary.txt` (добавить тип
  «final_summary» в reporter.ReportAllToFile — файлы `*_final_summary.txt`
  поедут в UI-архив отчётов автоматически).
- **UI**: новый эндпоинт `GET /api/sessions/{id}/summary` — JSON со всеми
  блоками (собирается из Report + EmulState.SnapshotJSON + новых счётчиков).
  Отдаётся в любой момент: посреди прогона — текущие значения, после — финал.
  Отдельная страница/вкладка «Summary» в SPA (ui/static): верхний блок итогов,
  таблица юнитов, топ ошибок полным текстом, инварианты/limbo/остановка,
  спарклайн поминутного таймлайна; автообновление 5 с во время прогона.
- **Общий код**: сборщик сводки — общий для CLI и UI (одна функция,
  принимающая collector/emulState/scheduler; CLI вызывает при остановке,
  session manager — на запрос эндпоинта). Никаких запросов к БД из сборщика.

### 2.4. Приёмка

- Любой CLI-прогон печатает блок и пишет `<csv>_final_summary.txt`.
- `GET /api/sessions/{id}/summary` отвечает 200 JSON во время и после прогона;
  страница «Summary» рендерит все блоки.
- Существующие 5-секундные статус-строки и ReportFinal — без изменений формата.
- Юнит-тесты: golden-тест текста сводки на синтетических счётчиках; тесты
  новых счётчиков; httptest эндпоинта (по образцу ui/emul_routes_test.go).
